# 缺陷记录

本目录记录已确认的缺陷：**现象、根因、实测证据、影响范围、修复与回归防线**。

与 `docs/research/` 的分工：research 记录「为了搞清某件事做了哪些调查」，bugs 记录「哪里坏了、为什么坏、怎么防止复发」。一个缺陷从调查中浮现时，调查过程留在 research，结论沉淀到这里。

## 为什么单独建这个分类

这批缺陷有一个共同特征：**它们都不会让任何测试变红**。

- 命令路由冲突：`cargo test` 全绿，冲突只在真实多包环境里出现。
- `hook-env` 每次全树扫描：功能完全正确，只是每次多花 ~400 ms。
- `exec` 重复安装：结果正确，只是每次多花 10 秒并重写磁盘。
- PowerShell 钩子粒度：行为正确，只是触发次数是其他 shell 的 20 倍。

功能测试证明「做对了」，却不证明「代价可接受」。所以每条记录都要写清**用什么手段才能抓到它**，并在修复时补上对应的测试或基准。

## 测性能时先确认测的是不是自己

004 有很强的自我污染能力，本目录的第一版数据就被它污染过，这里留作教训。

在装了 osdk 钩子的 PowerShell 里用 `& osdk ...` 计时，**每次 `&` 调用都会触发一次钩子**，于是量到的是「被测命令 + 一次完整激活」。当时据此得出「`hook-env` 要 1000 ms」，进而把 002 的根因误判成「单次太慢」。

改用 `-NoProfile` 加 `Diagnostics.Process` 直接起进程后，真实数字是 `hook-env` ~400 ms、应用其输出仅 ~1 ms。**结论完全变了**：单次代价没那么夸张，真正的放大器是 004 的触发频率。

所以性能基准必须在 `-NoProfile` 下、用不经 shell 管道的方式测量，并在文档里写明测法。

## 记录格式

每份文档包含：

1. **现象** — 用户看到什么。
2. **根因** — 精确到文件与行号，附源码片段。
3. **实测证据** — 本机可复现的数字，注明环境。
4. **影响** — 谁受影响、有多严重。
5. **修复** — 改了什么，为什么这样改。
6. **回归防线** — 哪个测试或基准能在它复发时报警。
