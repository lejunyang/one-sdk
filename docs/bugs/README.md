# 缺陷记录

本目录记录已确认的缺陷：**现象、根因、实测证据、影响范围、修复与回归防线**。

与 `docs/research/` 的分工：research 记录「为了搞清某件事做了哪些调查」，bugs 记录「哪里坏了、为什么坏、怎么防止复发」。一个缺陷从调查中浮现时，调查过程留在 research，结论沉淀到这里。

## 为什么单独建这个分类

这批缺陷有一个共同特征：**它们都不会让任何测试变红**。

- 命令路由冲突：`cargo test` 全绿，冲突只在真实多包环境里出现。
- 扫描下探安装负载：功能完全正确，只是每次多花几百毫秒，且随无关 SDK 增长。
- `exec` 重复安装：结果正确，只是每次多花 10 秒并重写磁盘。
- PowerShell 钩子粒度：行为正确，只是触发次数是其他 shell 的 20 倍。
- Windows POSIX shim 递归：生成的文件内容完全符合预期，**故障形态是「不返回」** —— 任何检查生成物的断言都会全绿，只有在真实 msys 下带超时实跑才抓得到。
- conda 元包命令归属：`bin_names` 的单包行为完全正确，测试全绿；只有在**元包**场景才静默退化成「暴露整个 prefix」，而这需要拿真实安装跑 `where --bins` 才看得见。

功能测试证明「做对了」，却不证明「代价可接受」。所以每条记录都要写清**用什么手段才能抓到它**，并在修复时补上对应的测试或基准。

## 测性能时先确认测的是不是自己

004 有很强的自我污染能力，本目录的第一版数据就被它污染过，这里留作教训。

在装了 osdk 钩子的 PowerShell 里用 `& osdk ...` 计时，**每次 `&` 调用都会触发一次钩子**，于是量到的是「被测命令 + 一次完整激活」。当时据此得出「`hook-env` 要 1000 ms」，进而把 002 的根因误判成「单次太慢」。

改用 `-NoProfile` 加 `Diagnostics.Process` 直接起进程后，真实数字是 `hook-env` ~400 ms、应用其输出仅 ~1 ms。**结论完全变了**：单次代价没那么夸张，真正的放大器是 004 的触发频率。

后来又踩了两个同类的坑，一并记下：

- **参数名撞了内建变量**。基准脚本的辅助函数用 `$env` 作参数名，它与 PowerShell 的 `$env:` 驱动器同名，传进去的环境被破坏，osdk 收不到正常环境而直接打印 usage。表现是「每次 12 ms、输出 0 字符」，看着像快得惊人，实际测的是报错路径。**基准必须断言退出码为 0 且输出非空**，否则量的可能是失败路径。
- **探针落在被测机制之外**。见 002 的变异测试记录，两种形态：探针放在超出扫描深度上限的位置，断言永远成立；以及在基准里**复刻一份被测判据**——它与产品代码脱钩，改判据后照样输出同一个数字，看起来测得很准，实际什么都没测。判断标准是「这个断言的结果会不会随产品代码改变」。

所以性能基准必须：`-NoProfile`、不经 shell 管道、断言退出码与输出规模、并在文档里写明测法。

这些约定已写进 `AGENTS.md` 的「交互延迟」章节，回归防线是 `crates/osdk-core/benches/interactive_latency.rs`。

## 记录格式

每份文档包含：

1. **现象** — 用户看到什么。
2. **根因** — 精确到文件与行号，附源码片段。
3. **实测证据** — 本机可复现的数字，注明环境。
4. **影响** — 谁受影响、有多严重。
5. **修复** — 改了什么，为什么这样改。
6. **回归防线** — 哪个测试或基准能在它复发时报警。

001 与 004 是各自独立的缺陷。**004 是当前最痛的一个**：它把 002 的单次代价乘上 22 倍，因此排在 002 之前修。002 单独存在时只是「每次提示符多 400 ms」，可以接受；被 004 放大后才变成「敲一条命令等 12 秒」。

002 分两阶段修完：第一阶段（manifest 处剪枝）只解决 12%，如实记为「部分修复」；第二阶段（按 namespace 裁剪）解决剩下的 88%。**分开提交而不是攒在一起**，是因为两者的风险完全不同——前者是纯局部优化，后者动的是「哪些目录会被扫到」，牵涉安全属性，需要单独的测试与变异验证。

006 与 007 都出在**跨进程边界的数据格式演进**上，且方向相反：006 是 serde 默认值让旧数据静默沿用旧语义（太宽容），007 是旧读侧遇到新字段直接拒绝服务（太严格）。两者共同的错误假设是「读侧与写侧同版本」。007 还是本批中唯一**在实现另一个功能时被动撞见**的缺陷——它提醒我们，只验证「新版本行为正确」不够，**升级路径本身也是需要测试的行为**。

008 是照着 006 自己写的告警去操作时撞上的：那条告警把用户指向 `shims.include`，而它是全局白名单，照做会把整条工具链关掉（646 个 shim 归零，`cargo`、`go` 一并消失）。**一条告警把用户导向了破坏性更大的操作**，比缺陷本身更值得警惕——修 008 时要连带修 006 的告警文案。

把 005 到 008 放在一起看，四个缺陷有同一个形状：**某个机制的作用域比它的名字暗示的要大**。005 是 DLL 按路径而非内容实例化，006 是「归属为空」被当成「归属未知」，007 是「读不懂」被当成「已损坏」，008 是「取回一个」被当成「只要这些」。
