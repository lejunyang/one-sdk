断裂点：pull 与 env 是两条不相通的路

全部实测

这不是配置疏漏。model pull 写到 <data>/models/，model env 指向 <cache>/pkg/models/，两者从未对接；启用 env 不会让任何工具看见 pull 的成果。

图 1.1 现状：一次 pull 与一次 env enable 在磁盘上落到两个互不相干的位置（临时 OSDK 根实测输出）

model pull 的产物

<data>/models/probe/
├── current.json   {"snapshot":"4d44c30c20f5efa903ebe9b0"}
├── .locks/
└── snapshots/
    ├── 4d44c30c20f5efa903ebe9b0/   第一次 --include

env 只影响「客户端库自己下载时落到哪」，与 pull 的成果无关。

六个结构性冲突与各自的解

正面回答，不回避

每一条都先承认冲突是真的，再说明为什么解法不是「让用户自己写配置」。

表 2.1 冲突 → 解法 → 该解法的代价

冲突为什么它是真的解法代价 / 边界
内容哈希 vs 稳定路径 哈希含文件选择；去掉这一点会让两次不同 --include 互相覆盖 不动快照，增加 <data>/models/<n>/current 目录级链接 Windows 用 junction（免提权）；符号链接在普通机器上会失败
一 repo 多类别 vs 一目录一类别 扩散仓库同一 repo 内含 unet/vae/text_encoder，分属三类；YAML 语义是一目录一类 渲染 ComfyUI 形状的 models 根，硬链接指回快照字节 需要「仓库路径 → 类别」映射；推不出的文件 不进视图 并报告
CAS 去重 vs 消费者要真实文件 —（这条比看上去小） 硬链接对消费者就是真实文件；HF 缓存实测用普通文件也能解析 跨卷不可硬链接（实测被拒），退化为 junction 或拷贝
不可变快照 vs 消费者就地写入 改硬链接 = 改同一批字节，会一起污染 CAS，verify 随后失败 ① 视图文件设只读 ② verify 覆盖视图 ③ 写入区与只读区分离 不做 CoW 拦截：用户态无法拦 open(O_WRONLY)
镜像便利 vs lock 可移植 自定义源会把镜像域名写进 lock（实测 endpoint = "https://hf-mirror.com"） 不放宽折叠规则，而是把常用镜像升格为 内置候选，天然落入折叠分支 私有端点继续原样入锁 —— 这是正确的
[models] 声明 vs trust 门禁 未识别顶层表 fail-closed 为 ExecutesCode，且 shim 也会拦（实测 exit=1） 加入 INSPECTED_TABLES 按 key 判定；affects_tool_dispatch 返回 false 忘了后半步 = 精确重演 [syspkg] 那次事故
trust 冲突已用对照实验确认，不是推断。两个项目唯一差别是后者多一段 [models.flux]：control-no-models 的 osdk current exit=0；with-models exit=1，报「project config contains trust-required fields and is not trusted」。

表 4.2 多根语义：追加一个 osdk 根到底意味着什么（probe_multiroot.py，真实 folder_paths.py）

问题答案实测细节
追加根与内置根等价吗？等价权重正常出现在对应类别，且不顶掉用户原有根的内容（两条断言分别验证「看得见新的」与「没弄丢旧的」）
两个根有同名文件？先注册者胜按注册顺序取第一个实际存在该文件的根（不是「第一个根」——内置根通常没有该文件）。get_filename_list 只列一次，UI 上看不出有两份
is_default 的作用？会反转胜者把该根提到搜索顺序最前，同名冲突的赢家随之改变。所以 osdk 视图不应加 is_default——那等于悄悄改变用户原有根的优先级
类别子目录必须齐全吗？不必须缺失的类别只是空列表，不是错误（该变异被标记 EXPECTED-SURVIVE 并确实全绿）。但仍建议全建 25 个，避免 Desktop 往只读视图里创建目录
目录需要可写吗？不需要只读权重文件仍被正常发现与列出 —— 这是「视图设只读」这条防线的必要前提
一个被捕获的自身错误。该探针第一版断言「冲突取 registered[0]」，结果 FAIL——因为 registered[0] 是 ComfyUI 内置根，两个文件都不在那儿。失败的是我的断言，不是被测机制。改成「按顺序找第一个真正存在该文件的根」并额外加了一条把结论讲明白的断言，比硬编码一个胜者更好：后者会在 is_default 改变行为时静默继续通过。

图 4.3 为什么 osdk 不该直接写 settings.json —— 三条独立证据

证据一 · 上游自己说
launcher 会覆盖它
Desktop 随包维护脚本原文：「Close the app before any mutating action — the launcher will overwrite settings.json / installations.json on its own save cycle.」
证据二 · 本轮实测到了
它在测试期间自己写了一次
installations.json 哈希变化，.bak 恰好轮转为变更前内容。diff 是纯增量 lastLaunchedAt，来自 Desktop 在 03:07:06 自动启动的它自己的实例。
证据三 · 回滚点会被消耗
.bak 只写第一次
脚本注释：legacy .bak「only written the first time, so the very first/original snapshot is preserved」。osdk 写坏了，用户唯一的原始快照可能已经没了。
采纳的替代方案：osdk model view path comfyui 打印视图根 + 一行指引，由用户在 Desktop UI 里一次性添加。此后 osdk 重建视图、切换快照、改 --include，这个路径都不变——稳定入口的意义正在于此。若将来 Desktop 提供受支持的 CLI/IPC 注入途径再补 attach 子命令；本轮在 asar 内未找到这样的途径。

05

目标架构：获取 / 存储 / 呈现三层分离

获取层语义一条不丢

重构不是推翻现有获取语义，而是补上从未存在过的第三层。快照仍然不可变、内容寻址、可 verify；视图是派生数据，可随时重建、随时丢弃。

图 4.1 三层架构 · 灰底为保留现状，橙色为新增

Acquire获取层改动：provider 注册表化 + 内置镜像
provider registry（取代闭合 enum）：hf · modelscope · 新增 http / local。镜像作为 provider 的内置等价端点参与测速排名与失败切换。产出已校验 SHA-256 的文件集。
▼
Store存储层改动：稳定入口 + 消除双份拷贝
CAS（blake3）+ 不可变快照 <data>/models/<n>/snapshots/<hash>/ —— 保留。新增 <data>/models/<n>/current 稳定入口（junction / symlink）；下载完成即 ingest 进 CAS，不再留独立第二份。
▼
View · 新增呈现层本重构的核心
<data>/views/<consumer>/<profile>/ 渲染成消费者认识的形状：
comfyui models 根 + 类型子目录（硬链接、只读）  hf-cache models--org--repo/{refs,blobs,snapshots}  gguf 扁平 *.gguf  a1111 异名类别目录
交付方式二选一或并用：① 生成消费者配置文件　② 导出环境变量（HF_HUB_CACHE / LLAMA_CACHE / MODELSCOPE_CACHE）
三层分离带来的性质：换 --include 导致快照哈希变化时，视图重建即可，消费者侧配置路径不变；同一份字节可同时被多个消费者看到而不额外占空间。

图 4.2 新增 CLI 面 · osdk model view

osdk model view add <consumer> --model <name> [--profile <p>]
                               [--map <repo-path>=<category>]... [--link-mode hardlink|copy|auto]
osdk model view list | path <consumer> | rebuild [<consumer>] [--prune] | remove <consumer>
osdk model view export <consumer> [--to <path>]   # 生成消费者配置文件
osdk model view doctor <consumer>               # 未归类文件 / 悬空链接 / 跨卷退化

既有命令保留语义：pull · sync · list · path · verify · remove
变更：model path --stable 打印稳定入口 · pull --as <consumer> 拉完即建视图
      verify 扩展到视图 · remove 先拆视图再删快照
view doctor 是设计的一部分，不是附属品。既然类别推断必须 fail-closed（推不出就不进视图），就必须有一个命令能回答「哪些文件没进去、为什么」。

watcher 用 Get-ChildItem | Measure-Object Length，连续八分钟报 0 MB。四种读法对照：

t=0  Get-ChildItem=1747484099  Get-Item=1801671300  FileInfo=1801671300  OpenStream=1801671300
t=1  Get-ChildItem=1801671300  Get-Item=1811413643  FileInfo=1811413643  OpenStream=1811479107

     ↑ 恒等于上一轮的 OpenStream 值

为什么不推荐 osdk 接管运行时：那等于用 osdk 解析出的 Python + torch 去替换一个上游已验证过的组合。收益是「统一管理」，代价是把 works-by-construction 的环境变成需要自己维持正确性的环境——而 torch/CUDA/Python ABI 的组合恰恰最容易出错。这与 osdk 对 Android SDK 的既有立场（不重新分发、不自己造一套）、以及 pypi: backend「把解析交给 uv」的判断同源。

表 7.3 三处张力，必须说清楚而非回避

张力说明与处置
autoUpdateComfyUI: true Desktop 会自行更新 ComfyUI 本体，osdk 锁不住。所以 osdk.lock 只保证模型可复现，不保证 ComfyUI 版本可复现。需要后者就在 Desktop 里关掉自动更新——那是 Desktop 的开关，不是 osdk 的。文档必须写明，否则「osdk 让它可复现」是空话
两个 uv 并存 Desktop 自带 uv 0.12.9（standalone-env\uv.exe），osdk 也管 uv。两者独立、互不干扰。不要让它们共用缓存：Desktop 环境是钉死的，改它的缓存只会制造难查的问题
模型有两条下载路 ComfyUI-Manager / 前端也能下模型，落到 is_default 标记的那个根（当前是用户的 Shared\models）。osdk 视图是另一个根且只读。这是好事——两者不互相污染，osdk 管的那部分保持可校验。这也是「不要给 osdk 视图加 is_default」的实际理由
什么时候才该考虑 osdk 托管源码版：需要钉死 ComfyUI commit 做可复现实验、需要非 NVIDIA 后端（Desktop 变体是 win-nvidia）、或需要在 CI / 无 GUI 环境跑。这三种情况前置是给 pypi: backend 增加「应用环境」模式（P3-3）。
