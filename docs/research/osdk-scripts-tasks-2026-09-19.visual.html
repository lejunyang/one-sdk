结论速览

六个决定形状的结论

内嵌脚本语言应该做，但不是第一步。真正的地基是「声明式 TOML + shell + 任务级增量」，内嵌语言是第四档的逃生舱。

推荐引擎
mlua + Lua 5.4
独立试验 +421.5 KiB，接入 osdk 实测 +304,640 B（+2.37%）。MIT，启动开销与基线无法区分。
shim 侧代价
0 字节
置于默认开启、shim 关闭的 scripts feature 后，osdk-shim.exe 字节数一字不差。两次独立构建实测。
坚决不做
pattern rule 与自动变量
引入它等于从任务运行器变成构建系统。mise / just / Task / cargo-make / npm / deno / turbo 无一提供——这是一致判断而非遗漏。
Windows 否决项
just 式「默认需要 sh」
just 官方：安装后 sh 必须在 PATH 中，即需 Git for Windows / Cygwin。这与 osdk「装上就能用」的价值主张冲突。

无

分层原则
升档不推翻
四档之间无一步需要先重写别的任务。20 个任务里 19 个停在第一档、1 个用第四档，是正常状态。

该抄

  • mise 的 sources/outputs，尤其是「任务定义自身自动算作 source」—— 改了定义就重跑。
  • mise 的 usage spec，且一步到位做 spec 式（不走它已废弃的模板函数弯路）。
  • mise 的 run_windows。（pwsh 自动 -NoProfile 不该抄 —— 初稿的错误结论，修正见第 07 节。）
  • Task 的 method: checksum|timestamp|none —— 判据做成可选项。mise 事后也补了 hash 选项，说明单一 mtime 不够。
  • mise 区分「run 内的执行步骤」与「depends 图的边」 —— 解决了 depends 表达不了的「先 A 后 B‖C」。

该避

  • just 的「Windows 默认需要 sh」 —— 对以「装上就能用」为卖点的 osdk 是致命的。
  • make 的 pattern rule 与自动变量 —— 见第 05 节。
  • npm 的「字符串直接丢给平台默认 shell」 —— 这正是 cross-env / rimraf 这类补丁包存在的根本原因。
  • mise 的 Tera 模板参数函数 —— 上游自己已废弃，并写明三条理由（两遍解析返回空串、转义不可预测、TOML 与 file task 行为不一致）。
  • mise 的 confirm 语义 —— 它只守 run，depends 已经跑完了（官方用 WARNING 标注）。osdk 若做确认应守住整个子树。
  • cargo-make 内嵌 duckscript 的选择 —— 实测 3,415 KiB，是 Lua 的 8 倍而表达力更弱。

为什么 pattern rule 不该做

它的本质是「用一条规则声明 N 条文件级规则」。一旦提供，用户合理期待的下一步是：自动推导依赖链（.c → .o → 可执行文件的传递闭包）、VPATH 搜索、双冒号规则、.SECONDARY/.INTERMEDIATE 中间文件生命周期管理。这不是「多做一个功能」，是变成构建系统。

而表 4.1 中该行七个工具全是 ❌ —— 这是七个独立项目的一致判断。真实世界里需要 pattern rule 的场景（编译一棵源码树）已由各语言自己的构建器（cargo / tsc / go build）承担，任务运行器的职责是以正确的工具版本和环境调用它们，并在输入没变时跳过。

mise 官方在 monorepo 文档里说得很直白：declare prerequisites in mise, or delegate the complete build graph to an existing build system. Avoid duplicating conflicting graphs.

06

四档分层设计

核心约束：升档不推翻

每一档都是上一档的严格超集，低档写法在高档存在时语义不变。用户永远不会因为某个任务变复杂而被迫重写其他任务。

第一档

单行字符串

[tasks]
build = "cargo build"
test  = "cargo test"
覆盖大多数场景。与 mise 的 trivial task 完全一致。项目里 19/20 的任务应停在这里。
第二档

多行 shell + 声明式元数据

[tasks.build]
run = ["cargo fmt --check",
       "cargo build --release"]
run_windows = "pwsh -File ..."
depends = ["fetch-deps"]
sources = ["crates/**/*.rs"]
outputs = ["target/release/osdk.exe"]
增量、依赖、平台变体、环境变量。Makefile 的绝大多数用途在此被覆盖。
第三档

独立脚本文件

[tasks.release]
file = "scripts/release.ps1"

# 或 osdk-tasks/ 目录
# 用 #OSDK / #USAGE 注释头
脚本超过约 20 行时挪出 TOML。好处是编辑器能提供语法高亮与 lint。
第四档

内嵌 Lua（可选 feature）

[tasks.sync]
lua = """
for _, t in ipairs(targets) do
  if osdk.platform.os == "windows"
  then osdk.sh(...) end
end
"""
只用于条件分支、循环生成、跨平台路径计算三类。字段名用 lua 而非 run，一眼可辨档位且能给出互斥报错。
↓ 加元数据，run 原样保留
↓ 脚本变长，挪进文件
↓ 确需程序化逻辑
← 逃生舱，不是地基

字段名 lua 是刻意的：若复用 run，就需要靠猜测内容格式来分派解释器；独立字段让「这是哪一档」一目了然，且 run 与 lua 同时出现时可以给出明确报错而非静默取其一。

否决了一批看起来自然的设计

mise 的 Windows 细节值得逐条抄：file task 可见性靠「扩展名在 exe/bat/cmd/com/ps1/vbs 白名单内 或 有 shebang」判定（两者都没有的文件在 Windows 上完全隐形）；Windows PowerShell 拒绝执行非 .ps1 脚本，所以 pwsh 任务被复制成临时 .ps1 再跑，并用 MISE_TASK_DIR 让脚本定位自身；cmd /c 不能直接启动 .ps1，所以要写 pwsh -File ... 而非直接写路径。

修订：mise 的 -NoProfile 不能照抄

mise 在 shell 为 pwsh/powershell 时自动传 -NoProfile，理由是「防止会修改 PATH 的 profile 遮蔽任务自己的工具」。初稿建议照抄，这条结论对 osdk 是错的，此处修正。

osdk 的 PATH 注入有两套独立机制（activate/mod.rs:3-9）：shims 写进持久 PATH，禁用 profile 也照常继承；shell activation 则完全挂在 profile 钩子上。因此 -NoProfile 的后果是分层的，既不是「全丢」也不是「无影响」：

能力-NoProfile 下原因
调用 node / cargo / go正常且版本正确shim 被调用时现场解析项目配置
JAVA_HOME / GOROOT 等不会被设置由 hook-env 导出
被 ShimSettings 排除的工具找不到只有 activation 会前置真实 bin 目录

本仓库 AGENTS.md「与 sdk 有关的命令不要使用 -NoProfile」因此是准确的，与 mise 的做法真实冲突。正确做法：默认不加 -NoProfile，改由 osdk 在启动任务前自己计算并注入环境（复用 hook-env 逻辑），同时设 OSDK_TASK=1 让 profile 钩子自避让。两个目标同时满足，而 -NoProfile 只能满足其一。

另：用户为本项目写的脚本需兼容 PowerShell 5.1，因此 osdk 生成的任何 .ps1 片段必须限制在 5.1 语法内：不用 &&/||、不用三元 ?:、不用 ??、不用 ConvertFrom-Json -AsHashtable。

表 7.2 & 的三种互不兼容语义 —— 本机实测（pwsh 7.6.6）

shella & b 的含义实测证据
Unix sha 放后台，b 立即开始（并发）通识，本机未验证
Windows cmda 跑完再跑 b，无条件输出 RAN_ANYWAY、exit=0 —— 前一条的失败被吞掉
PowerShell 7尾随 & = 后台 Job500 ms 的 sleep 在 260 ms 返回，确为异步
PowerShell 5.1parse error「不允许使用与号(&)。& 运算符是为将来使用而保留的」

cmd 的 & 与 Unix 的 & 语义完全不同：前者是「无条件顺序」，后者是「并发」。同一份 run 在两个平台上做两件不同的事，而且都不报错。
设计约束：run 内不依赖 &，两个诉求各给专门字段 —— 失败也继续用 { cmd = "…", ignore_error = true }（对齐 make 的 - 前缀、Task 的 ignore_error、cargo-make 的 ignore_errors）；真并行用 { tasks = ["a","b"] }，osdk 能等待并收集退出码，而 & 扔出的后台进程无人回收。depends 不能替代后者：官方明确其顺序不构成序列，表达不了「先 A，再 B‖C」。

实测中发现：sh 可能是 osdk 自己的 shim

本机 Get-Command sh 解析到 E:\osdk-data\data\shims\sh.cmd。这意味着在装了 osdk 的开发机上 sh 确实可用 —— 但这恰恰让「默认 shell 选 sh」更危险：开发机上因为这个 shim 悄悄能跑，裸机用户却会失败，问题被推迟到用户侧才暴露。默认 cmd /c 的结论因此更稳固。

为什么 Lua 选 5.4

  • 5.4 是当前维护版本，也是 mlua 默认档与 vendored 构建最顺畅的一档。
  • 5.3 起的整数子类型让路径拼接与数值计算不会莫名产生 1.0。
  • LuaJIT / 5.1 的优势只有生态（老库、OpenResty 系），而 osdk 不消费第三方 Lua 库，该优势为零；LuaJIT 的汇编后端在 aarch64-windows 一类目标上反而是负担。
  • 体积差异不构成依据 —— 各版本都在数百 KiB 量级，远小于候选引擎之间的差距。

结论：选 5.4 是「采用默认值」而非权衡结果，但这个默认值没有需要推翻的理由。

为什么不要 Luau 的沙箱

  • 代价：+323.5 KiB，且构建期依赖从 C 抬升到 C++。
  • 它提供只读全局表、屏蔽 debug/io/os、指令与内存配额 —— 目标场景是「执行不可信的第三方代码」（来源 Roblox 要跑玩家脚本）。
  • 而 osdk 的任务来自已过 trust 门禁的 osdk.toml，同一文件的 run 本就能执行任意 shell 命令。
  • 在一个已能执行任意 shell 的文件里给 Lua 加沙箱，不构成任何实际保护 —— 攻击者直接写 run 即可。

若将来支持远程任务定义（当前明确不做），信任边界才会改变；但届时正确答案多半是进程级隔离而非语言级沙箱，因为 run 的问题依然存在。

实测中踩到的两个陷阱

必须写进设计约束

这两个都是我在本次实测中亲自踩到的，不是从文档推断的风险。它们的共同点是：失效时不报错、看起来完全正常。

8.1 glob 全量遍历 —— 46 倍的差距

在 target/ 旁运行
2,827.91 ms
干净目录（201 文件）
61.26 ms

这不是设计的成本，是我的 harness 的缺陷：WalkDir::new(".") 从 cwd 全量遍历，而 cwd 旁边就是几 GB 的 target/。但它精确预演了产品会怎么出问题 —— AGENTS.md 里「扫描下探进 conda prefix，一次多走 1,000 个目录」记的是同一类坑。
→ 设计约束：freshness 扫描必须从 glob 的字面前缀起步（src/**/*.rs 只进 src/），绝不能从 cwd 全量 walk。mise 官方文档也有对应警告，且它已把 monorepo 的自动文件系统遍历发现废弃，改为显式声明。

8.2 glob 静默失配 —— 检查悄悄什么都没做

写法匹配到的文件表现是否报错
sources = ["**/*.marker"]0 个freshness 检查静默跳过，任务每次都跑否 —— 看起来完全正常
sources = ["./src/f1.marker"]正确匹配output 新 → up to date；touch source → 重跑—

原因：WalkDir 产出的路径带 ./ 前缀而 pattern 不带。→ 设计约束：glob 规范化（是否带 ./、路径分隔符、大小写）必须有双向测试 —— 「该匹配的匹配到」和「不该匹配的没匹配」，否则失效是静默的。这正是 AGENTS.md「前缀匹配过宽，与写窄同样危险，而且更隐蔽」那一条的形态。

9.2 信任模型 —— 现状核查结果是个好起点

核查 trust.rs 发现：collect_requirements 对未知顶层表 fail-closed，归为 ExecutesCode。这意味着 一旦 osdk.toml 出现 [tasks]，现有 osdk 会立即要求显式 trust —— 无需改动任何代码，默认就是安全的。

要做的事为什么
把 tasks 加进 TRUST_REQUIRING_TABLES 并标 ExecutesCode不是为改变行为（fail-closed 已如此），而是让拒绝信息能说清「tasks —— 会执行任意代码」，而非笼统的未知表
task_config 与 vars 同样显式分类为 ExecutesCodetask_config.shell 直接决定用什么解释器跑所有任务；vars 会被插值进命令。不要因为「看起来只是变量」就放进安全列表
