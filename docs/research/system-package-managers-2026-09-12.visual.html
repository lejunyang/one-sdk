设计立场：四条不可协商的边界

先读这里，后面六张图都是它的展开

osdk 对系统包管理器只做四件事：发现、状态查询、镜像探测与配置建议、显式 apply。反过来说，有四件事它明确不做——这不是能力缺口，是定义边界。

不接管安装目录

Homebrew 的 prefix 事实上固定，winget 仅 portable 类型可控。诚实的结论是不去争夺这个控制权。

不纳入 shim 体系

系统包不产生 shim、不参与 Backend 的 vtable，因此对 osdk-shim 的体积增量是 0 MB。

不进 lockfile 的可复现性承诺

宿主包管理器的版本解析不在 osdk 控制之下，写进 lockfile 只会给出虚假的可复现保证。

永不隐式安装

只有显式 apply 会改动系统，且过程非事务性。诊断与状态查询永远是只读的。

需要真正的目录控制与可复现性时怎么办？走 osdk 自有的下载安装通道（现有 backend 体系），而不是系统包管理器。两条路径的能力承诺不同，混用才是问题的根源。

shim 只负责把已安装工具解析出来再 exec。syspkg/ 既不在 vtable 里，也没有任何从 shim 出发的调用路径，因此在 release 构建中被整体裁掉——前提是 shim 仍然独立于 CLI 单独构建。

为什么不复用 Backend？表面上「装一个包」和「装一个 SDK」很像，但两者的承诺完全不同：backend 承诺目录布局、版本解析与可复现性，系统包管理器这三项一项都给不了。强行套用同一个 trait，得到的不是复用，而是一个处处需要返回「不支持」的实现，外加下一节列出的全部体积代价。

统计口径：每列各按其 11 项已判定维度计数，「未评估」格不计入。winget 与 Homebrew 沿用原有 11 维口径，数值不变。

Linux 三家为何不能与 winget / Homebrew 同级：它们在机器可读输出与镜像换源两个维度上反而强于 winget（apk 的 --format json 是全表最强，三家都能镜像包本体而非仅索引）。但在权限与事务性 / 回滚上是结构性劣势——变更一律需 root，且都没有事务撤销（仅 dnf 有 history undo，不在本矩阵内）。这决定了它们在 osdk 中应降级为「只读检测 + 建议命令」，而不是与 winget / Homebrew 同级的 provider。

读这张图的方式：Homebrew 在输出契约上明显更好，却在安装目录上与 Linux 三家同为「不可行」；winget 反过来——目录尚有 portable 一线可能，但输出与退出码全线需要变通。没有任何一侧是「更适合做 backend」的，短板只是落在不同位置。这就是结论只能是「另立子系统」而非「扩展 Backend trait」的实证依据。

mise 的两套做法

winget 侧是真代理（shell out 到 winget.exe，用 --id --exact + silent + 接受协议）；brew 侧完全自实现——从 formulae.brew.sh 取元数据、从 ghcr.io 下 bottle、自己做 relocate / 重签名 / link，从不 shell out 到 brew。

mise 的定位选择

系统包放在独立的 [bootstrap.packages] 而非 [tools] backend，刻意不给 shim、不按项目 pin。明确不支持 Intel Mac，明确「永不隐式安装」（只有 apply 会装东西），非事务性。

osdk 的取舍

与 mise 的定位一致但更保守：两侧都以代理与诊断为主，不复制 brew 自实现那套 relocate / 重签名负担。需要真正的目录控制与可复现性时，走 osdk 自有下载安装通道。

探测 ≠ 改配置探测结果默认只作为建议呈现。真正写入宿主配置必须经显式 apply，与 container/ 的镜像 apply 同样要求确认。
换源本身可能被禁winget 的 source add/remove/reset 需要管理员权限，组策略 EnableAllowedSources 可完全禁止换源。osdk 须把这种情况作为正常结果诊断出来，而不是当作失败重试。
显式优先级
  1. 用户显式 pin
  2. 新鲜缓存中的排序结果
  3. 本次并发探测的打分排序
  4. 按序回退的下一候选

winget 侧必须说清的期望管理：用户配置镜像后若发现「搜索变快了但安装还是慢」，这不是配置错误，而是 winget 镜像模型的固有属性。osdk 的诊断输出应当主动说明这一点，避免用户反复折腾本就无法通过换源解决的下载速度问题。

同时要排除一个误解：Linux 侧不存在「缺少 codesign」的缺口。ad-hoc 重签名是 macOS arm64 独有的硬要求（Apple 官方：「any executable must be signed before it's allowed to run」，且不适用于 Rosetta 2 与 Intel）；Linux 的 ELF 改写不涉及签名；Linux 也无默认生效的用户态强制签名校验（CONFIG_IMA_APPRAISE 上游 default n，且 arch policy 只覆盖 kexec / module / firmware / policy，不含一般可执行文件）。需要它的平台恰好就是有它的平台。
测量口径与已知偏差 · 必读
  • 最终二进制口径：全部数字为链接 + strip 后的 .exe 字节数，在 Windows x86_64-pc-windows-msvc、cargo/rustc 1.98.0 上实测。probe 复制了 osdk [profile.release] 的全部设置（opt-level="z"、lto="fat"、codegen-units=1、strip、panic="abort"，以及六条 per-package opt-level=3）。
  • Windows 上的数字是偏小的下界：apple-codesign 与 object 的 Mach-O 路径在 macOS 目标上会有更多平台相关代码进入链接，真实 macOS 产物只会更大。
  • 方法论陷阱（这组数字为何可信）：lto="fat" 会裁掉未被真正调用的代码。浅探针测 apple-codesign 只有 +15 KB，改成真实调用签名路径后是 +1,680 KB，相差约 100 倍；resolvo 用 size_of 探测时甚至与基线逐字节相同。因此本节数字全部来自「真实驱动主路径」的深探针，而非浅引用。
  • resolvo 的 0 MB 仅对 osdk-cli 成立——它已经因 rattler 的 conda 支持存在于依赖图中，对其他项目不可直接套用。
  • codesign shell out 的 0 KB 是纯体积口径，不含可用性代价（见图 5e：它需要 Xcode Command Line Tools）。测量时探针在 Windows 上必然走 Err 分支，这不影响体积结论，但未验证该命令的实际行为。
  • F1 / F2 是直接测量的合并配置，而分组数字不可相加——各组之间共享传递依赖，逐项累加会高估。绝对预算必须以 F1 / F2 的合并测量为准。
  • 未测源码构建路径：「无 bottle 时的源码构建」（mise 用了内嵌 ruby + 自有 Formula-DSL shim）未纳入测量，因为 osdk 不可能做这块，已从预算中剔除。

这一节如何支撑设计结论：本轮重测把结论推得更硬了。自实现路线在体积上不是「贵一点」——纯 Rust 签名越线 2.4 倍，而即便取最便宜的可行组合 F1，也仍越线 1.31 倍，中间不存在「勉强能接受」的选项。更重要的是，上一版寄望的两条退路都被本轮否掉：版本对齐只能省下 0.49 MB，剩余 1.43 MB 是 OCI 本体成本；而「签名 shell out 归零」要以依赖 Xcode Command Line Tools为代价，恰好破坏 bottle 免开发者工具这一前提。mise 能承担 brew 侧完全自实现，是因为它的体积约束与 osdk 不同；osdk 选择代理路线，是被这组实测数字确定下来的，而非偏好。
