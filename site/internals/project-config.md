# 外置项目配置绑定

用户视角的用法见 [外置项目配置](../guide/project/external-config)。本页说明
这套机制的设计取舍：为什么物理配置路径与逻辑项目根分离、root-id 为什么是
内容派生的路径哈希、以及哪些静默状态被刻意改成了 fail-closed。

## 动机：本地配置优先模型的盲区

既有模型假设项目配置总是项目目录里的 `osdk.toml`：发现从 cwd 向上走，
`use`/`lock` 写回同目录，信任记录挂在那份文件上。这个模型覆盖不了三类
常见场景：只读检出的第三方仓库、不能动文件的代码库、以及希望把配置集中
托管在自己 `OSDK_CONFIG_DIR` 下的多项目机器。外置绑定的设计目标是**不新增
第二套配置格式**——外置目录里放的就是普通 `osdk.toml` 与 `osdk.lock`，
只是物理位置在配置目录下，再用一个锚点文件把它指回真实项目根。

## root-id：内容派生的目录名，而不是一份索引

`<config>/projects/<root-id>/` 的 `root-id` 是项目根路径的完整 BLAKE3
（平台感知的规范化路径身份），刻意不使用项目名或 Git remote：

- 项目改名、remote 变化都不应改变「这个绑定是哪个项目」；名字与 remote
  都是可变标签，路径身份才稳定。
- 目录名即身份，因此**没有另一份可编辑的索引文件**。`<config>/projects/`
  目录本身就是注册表：枚举它即可发现全部绑定，手工编辑索引带来的
 「索引指向不存在的目录」一类不一致从设计上不存在。
- `project.toml`（schema = 1）只记录一件事：`root` 是真实项目根的绝对
  路径。物理目录与逻辑根分离后，运行时需要一个显式锚点来回指——否则
  「配置在 X、项目在 Y」的对应关系无处安放。
- 路径身份由 OS canonicalize（dunce）解析后的真实路径决定：junction、
  8.3 短名、大小写别名都归到同一身份；大小写按文件系统语义处理，osdk 不
  额外全小写，也不做 Unicode 规范化。因此同一目录的不同写法只会产生一份
  绑定。

## 单写源选择：配置与锁成套，禁止跨来源借用

cwd 逐祖先查找时，候选同时包括本地 `osdk.toml` 和已绑定的外置项目。
选择规则：

1. 最近项目胜出；
2. 同一项目根上，本地配置优先于外置配置；
3. 近的外置子项目可以胜过远的本地父项目。

一旦选定来源，**`osdk.toml` 与 `osdk.lock` 永远成套使用**：

- 绑定出生即自带最小合法锁（`add` 原子写入 `osdk.lock`，内容为
  `schema = 3`）；日后锁若缺失（如人为删除），按当前选中来源在同目录内
  重建，绝不跨来源借用另一份锁。两种 lock 混合会得到一份「配置来自 A、
  解析结果来自 B」的环境，比缺锁更难排查；
- 选中的配置或锁损坏时直接报错，不回退到另一份来源——静默回退会让用户
  以为外置配置生效了；
- 被 shadowed 的外置配置正文不读。最危险的静默分叉是「本地文件存在但
  内容不全，osdk 顺手补上了外置正文」；规则是 shadowed = 完全不读，
  只在 stderr 警告里说明采用与忽略的来源；
- `current`、`where`、`exec`、shim、shell hook 与 `use`/`config`/`source`
  共用同一份来源解析，避免「激活用一套、写锁用另一套」。

运行时对 lock 的消费语义不随外置绑定扩大：外置项目只是换了 lock 的
物理位置，不新增逐工具混合或跨来源合并。

## 逻辑根与物理路径分离的三个后果

- **相对路径按逻辑根解析。** 任务、deps 与相对资源路径相对于被绑定的
  项目根（或声明所在文件），而不是外置目录。外置目录在配置目录下，
  按它解析会指向完全错误的位置。
- **`extends` 保留逻辑祖先与仓库边界。** 边界按逻辑项目根向上找 `.git`
  确定，越过它的引用照旧报错，外置绑定不豁免；找不到 `.git` 时保留原有
  继承行为。
- **信任按真实配置文件审批，relocate 触发重审。** trust store 关联配置的
  真实路径、项目根与受管内容哈希。`relocate` 移动了物理目录，信任记录
  随之失效，需要重新 `osdk trust`。这是刻意的：如果信任自动跟随，一份
  已审批配置可以通过 relocate 扩大到新路径，等于审批面被悄悄改写。

## 写边界：外置配置不承诺项目零写入

外置 `osdk use npm:xxx` 走隔离安装，不碰项目的 `package.json` 与原生
lock——配置本来就不在项目里。但 `osdk run`、`osdk deps` 仍然按逻辑项目根
写构建产物与依赖目录。因此文档不做「外置配置 = 只读项目」的承诺，避免
用户把它用在真只读卷上后期望落空。

## 故障模式与处置

| 状态 | 处置 |
| --- | --- |
| 绑定目录里已存在本地 `osdk.toml` | 允许绑定；本地文件胜出，外置被 shadowed，stderr 警告 |
| 重复 `add` 同一目录 | 不覆盖已有绑定 |
| 选中配置/锁损坏 | 直接报错，不回退来源 |
| 绑定的项目根在磁盘上已不存在（missing） | 纯文本 `list` 的 `status` 与 `show` 的 WARNING 行直接暴露（`project root missing` / `config missing`），`--json` 另给 `root_exists` / `config_exists` / `missing`；`relocate` 保留配置与锁；不自动删除 |
| `remove` | 只删外置绑定目录；项目文件与共享安装池不碰；`--dry-run` 预览 |

## 明确不做

- 不猜 Git 根：`add` 精确绑定给定路径，避免「绑定到的目录」与「用户以为
  的项目根」不一致；
- 不自动安装任何工具；
- 没有 Git remote、分支、multi-profile 概念——绑定就是路径绑定，切分支
  不换配置；
- 不在项目目录里生成任何文件。
